# CLAUDE.md — Certo

Project memory for Claude Code. Read this first, every session.

## What this project is

A **coding/software agent harness built on the OpenHands Software Agent SDK**.
Give it a task; it uses tools (terminal, file editing, plus our custom tools) in a
loop until the task is done. The LLM provider/model is chosen entirely via `.env`
so it stays **model-agnostic**.

The full build plan lives in @docs/history/SPEC.md. Follow it milestone by milestone
(section 11 of the spec). The kickoff prompt is in @docs/history/KICKOFF.md.

**Four planning files, one question each** (this file is durable
rules/guardrails):

- @ROADMAP.md: where Certo is going and why (vision, themes, non-goals).
- @TODO.md: everything still to do, including known bugs and release
  chores. Check it before starting work, so nothing is forgotten.
- `ARCHITECTURE.md`: how each module works, SDK gotchas and internal
  limitations. Read it before touching SDK-facing code.
- `DECISIONS.md`: why past choices were made. Read the relevant entries
  before changing a behaviour an earlier decision settled.

These instructions govern development of the harness itself. They do not
automatically govern projects generated by the harness; generated projects
receive guidance through the shared skill catalog, task context, and any
project-specific `AGENTS.md`.

**SDK-drift warning:** the SDK details in `docs/history/SPEC.md` are historical and may
be stale. Treat every unconfirmed SDK symbol as verify-first (golden rule 2),
including symbols previously described as verified. See `ARCHITECTURE.md` for
known drift findings and corrected patterns. Re-verify SDK behavior after upgrades.

## The golden rules

1. **Build ON the OpenHands SDK. Do not reinvent it.** The agent loop, tool
   protocol, provider routing (LiteLLM under the hood), and sandboxing are the
   SDK's job. Our code is only: config, custom tools, an interface, and policy.
2. **Verify SDK symbols before using them.** The OpenHands SDK is young and its
   API still shifts. Before using any SDK class/function you have not already
   confirmed in this repo, check the live docs or the SDK's own `examples/`
   directory (see "SDK references" below). Prefer `get_default_tools()` over
   importing individual tool classes by name. Use `/verify-sdk` for this.
3. **Preserve the model-agnostic invariant.** Switching provider must require
   editing only `CERTO_LLM_MODEL` in `.env` — never a code change. Do not hardcode a
   model, provider, or base URL anywhere in `src/`.
4. **Never read or print secrets.** `.env` holds real keys and is git-ignored and
   permission-denied. Use `.env.example` for structure. Never echo key values.
5. **Never assume an ecosystem.** Inspect project metadata, configuration, and
  existing scripts before selecting commands or conventions. Do not assume
  Python, pytest, npm, or a particular framework.
6. **Separate guidance from enforcement.** Skills and prompts guide the LLM;
  harness code must enforce iteration limits, verification, retries, and
  explicit completion states wherever possible.
7. **Do not trust `finish` as proof of completion.** Acceptance criteria must
  be checked, and available verification must pass. If verification is
  unavailable, report the result as unverified rather than successful.

## Tech stack

- Python 3.12+
- `openhands-sdk` + `openhands-tools` — a **matched set**: always install/upgrade
  both in one command at the same version, or imports break.
- `python-dotenv` (config), `pytest` (tests), `ruff` (lint/format).
- Package uses a `src/` layout; code lives in `src/certo/`.

## Environment

This project uses **uv** for the virtual environment and dependencies. Run every
Python command through `uv run ...`, which uses the project's `.venv`
automatically — no manual activation needed. Install deps with
`uv pip install -e ".[dev]"` (resolves everything from `pyproject.toml`). Never
install into system Python — it's PEP 668 externally-managed and will error. If a
command seems to hit the wrong interpreter, or an install fails with
"externally-managed-environment", something bypassed uv: stop and ask me rather
than reaching for `--break-system-packages` or `sudo`.

## Commands

`uv run` executes inside the project venv automatically.

```bash
# Setup — installs the harness + all deps from pyproject.toml:
# openhands-sdk & openhands-tools (same version), python-dotenv, and dev tools.
uv pip install -e ".[dev]"

# Run the harness
uv run python -m certo "your task here"

# Test / lint
uv run pytest -q
uv run ruff check .
uv run ruff format --check .
```

Add new dependencies to `pyproject.toml` (don't `pip install` them ad hoc), and
keep `openhands-sdk`/`openhands-tools` pinned to the same version.

## Code conventions

- Small, single-purpose modules matching the layout in @docs/history/SPEC.md section 5.
- Custom tools follow the SDK's **Action / Observation / Executor** pattern
  (spec section 7); mirror `examples/01_standalone_sdk/02_custom_tools.py`.
- Each custom tool's executor must be unit-testable with a constructed Action and
  **no LLM/network call**.
- Type-hint public functions. Keep prompts and task text out of source — pass them
  in at call time.

## Testing rules

- `tests/` mirrors `src/certo/`.
- Tool executors are tested directly (no LLM).
- Any end-to-end test that needs a real API key must **skip cleanly when the key
  is absent**, so CI passes without secrets.
- Run `uv run pytest -q` after each milestone; do not move on with failing tests.

## Versioning

Every change that adds a feature bumps the third digit of the version
(`0.1.2` → `0.1.3`), in the same commit as the feature. Bug fixes and docs
alone don't bump it. The first two digits change only when the user decides
on a bigger release. Never reuse a number: PyPI rejects it, even if that
version was deleted. A bump updates three places, which
`tests/test_version.py` checks agree: `version` in `pyproject.toml`,
`__version__` in `src/certo/__init__.py`, and `uv.lock` (run `uv lock`).
`certo --version` prints the result.

## Working style

- Implement one milestone at a time (spec section 11). After each: run tests,
  then briefly report what changed and what's next. Use `/next-milestone`.
- Milestone 3 (the provider-swap proof) was run on 2026-10-19:
  `docs/benchmark/provider-swap-0.1.19.md`. Re-run it the same way after a
  change to config or LLM building.
- Ask before adding heavy optional pieces (Docker execution, server mode) — they
  are section 9 / "optional", not part of the core.

For non-trivial changes, inspect the controlling code path before editing,
identify a focused check that could disconfirm the current hypothesis, make
the smallest coherent change, and run that check immediately afterward. Use
the applicable skills rather than duplicating their detailed guidance here.

## Working agreements

Standing rules for every change, agreed with the Author. Every Claude Code
prompt written for this project must follow them.

1. **Docs in the same change.** Every change that touches a command, flag,
   setting, verdict, behaviour or known limitation updates the matching
   page under `docs/` in the same change (see "Keep docs/ up to date"
   below). Prompts list the docs update as an explicit numbered item, not
   an afterthought. `MANUAL.md` is superseded by `docs/`.
2. **Better on local models, never worse on cloud ones.** Certo is
   model-agnostic; local models are one use, not its identity. The quality
   goal is better results from local models (e.g. `qwen3.8:27b` via
   Ollama) without degrading results from mainstream cloud models (Claude,
   GPT, Gemini). Strategies aimed at weaker models are opt-in or gated by
   model tier, and every such change is checked with the benchmark on both
   a local and a cloud model before release.
3. **Measure before claiming.** Quality improvements are judged by the
   benchmark (`certo bench`, hidden tests), not by single runs or
   impressions.
4. **Prompts don't publish.** Claude Code sessions never tag, push or
   publish; the Author does that after review. One commit per numbered item.
   Stop and ask on decisions not covered by the prompt. The full test suite
   passes with no API key.
5. **Real runs only.** Reports never claim a live result that wasn't run in
   that session.

## Keep docs/ up to date

`docs/` is the user-facing documentation: short pages in four kinds, kept
separate — `getting-started.md` (one path, start to finish), `guides/` (how
to do one thing), `reference/` (complete and exact), `concepts/` (why and
how) — plus `troubleshooting.md`. `docs/README.md` routes readers to them.
`README.md` is only a quickstart that links into `docs/` with absolute
GitHub URLs (it is also the PyPI page). `MANUAL.md` is now only a redirect
table from the old manual's sections to the new pages.

Any change to a command, flag, setting, verdict, behaviour or known
limitation must update the matching `docs/` page **in the same change**,
not as a follow-up:

- A new/changed command, subcommand or flag → `docs/reference/commands.md`
  (and the guide that uses it).
- A new/changed `CERTO_*` setting → `docs/reference/configuration.md`.
- A new/changed verification state or exit code → `docs/reference/verdicts.md`.
- A change to what is checked per language → `docs/reference/verification-by-language.md`.
- A new execution mode, backend, server endpoint, or a change to how tools
  register → its guide and reference page.
- A newly discovered gotcha, bug workaround, or limitation (like the
  `python-dotenv` inline-comment quirk) → `docs/troubleshooting.md` or the
  "Known limitations" list in `docs/README.md`, instead of letting it live
  only in a commit message or PR description.

`tests/test_docs.py` enforces part of this: it fails when a `CERTO_*`
setting, an argparse flag or subcommand, or a verification state is missing
from its reference page, or when a relative link between Markdown files
points at a missing file or heading. It can't check that prose is still
true, so read the matching page when behaviour changes.

Write for users, in plain language (many readers aren't native English
speakers): output samples come from real runs or tests, not invented.
Maintainer notes ("verified live", SDK source references, bug archaeology)
stay in `ARCHITECTURE.md`, `DECISIONS.md` or `CONTRIBUTING.md`, not in
`docs/`.

Update documentation only when behavior, configuration, architecture, or a
known limitation changes. Keep implementation history in `DECISIONS.md` and
avoid duplicating the same detail across `CLAUDE.md`, `docs/` and the
planning files.

## Keep the planning files up to date

They exist so a future session doesn't have to re-derive project history
from conversation scrollback. Update them in the same change:

- **`TODO.md`**: add an item the moment it is found (a bug, a deferred
  step, an idea the user approves for later). Delete it in the change that
  does it; git history and the release notes keep what was done. One short
  entry each: what, why, when it counts as done.
- **`DECISIONS.md`**: one entry for every non-obvious choice a future
  session would otherwise re-litigate: the decision and its one-line
  reason. Append-only; a later decision says what it supersedes.
- **`ARCHITECTURE.md`**: when a module's role changes, or a new SDK-drift
  gotcha or internal limitation is found (add it there, not only as a code
  comment or a chat reply).
- **`ROADMAP.md`**: rarely, when a theme is finished or the priorities
  change. No file or function names; those belong in `TODO.md`.

Keep entries terse. This file (`CLAUDE.md`) stays focused on durable rules;
fast-moving status lives in `TODO.md` instead of being duplicated here.

## Gotchas

- `openhands-sdk` and `openhands-tools` version mismatch → `ModuleNotFoundError`
  on `openhands.sdk.*`. Fix with `uv pip install -e ".[dev]"` (or pin both to the
  same version in `pyproject.toml`).
- Model ID strings (e.g. `anthropic/claude-sonnet-4-5-20250929`) change over
  time — verify current IDs against provider + LiteLLM docs, don't assume.
- Individual built-in tool class names have varied across SDK versions — that's
  why the default path is `get_default_tools()`.
- In `.env.example` (and any `.env` Certo writes), a comment goes on its own
  line above the setting, never to its right: `python-dotenv` can read a
  trailing `# comment` as the value. `tests/test_config.py` enforces it.
